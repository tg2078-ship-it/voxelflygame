# VOXEL AIRRUN 4.2 — 연속 비행과 테마 모델 순환

## 비행을 반복해서 멈추던 원인

4.1의 `renderer.frame()`은 가까운 충돌 모델의 LOD0가 없으면 `flying → preflight`로 전환했습니다. 이때 기본 모델이 이미 준비되어 있어도 기체 선택, 경로 다운로드, 지형·모델 결합, GPU 예열 전체를 다시 실행했습니다. 짧게 비행한 뒤 반복해서 로딩하는 실제 사용자 증상과 일치하는 코드입니다. CPU 생성 검사만으로 이 문제를 발견하지 못했습니다.

4.2는 해당 자동 전환 분기를 제거했습니다. `FlightStream`이 첫 테마 전체의 충돌 호환 기본 LOD와 프록시를 출발 전에 준비하고, 다음 테마는 전환 45초 전부터 준비합니다. 기본 LOD는 현재·다음 테마에서 사용하는 동안 캐시에 유지합니다. 필수 기본 모델 요청이 장식·고화질 요청보다 먼저 처리됩니다. 고화질 LOD가 늦으면 이미 준비된 기본 LOD로 정적 모델과 네이티브 애니메이션을 표시하면서 교체합니다. 출발 준비는 진행 수량을 표시합니다.

`WorldView`에 실제로 결합되거나 네이티브 인스턴스로 추가된 모델만 충돌을 활성화합니다. 늦게 나타난 모델이 전방 1.3초 이내에서 갑자기 충돌을 활성화하지 않도록 여유를 둡니다. 모델 다운로드 실패·결합 지연 때 보이지 않는 구조물에 충돌하거나 카메라가 그 구조물을 피하는 상황을 막습니다. 요청 실패는 배경에서 재시도합니다. 일반 비행에서 고화질 모델 요청 때문에 전체 출발 로딩을 다시 실행하지 않습니다. 초기 출발 로딩, 사용자의 일시정지, E 경로 계획은 별도 기능입니다.

모델 결합을 작업 스레드로 보내기 전의 큰 버퍼 복사도 작은 작업으로 나눕니다. 교차 배열의 여러 속성, 동일 형상의 여러 재질 구간은 각각 원본 데이터의 단일 사본을 공유합니다. 라이브 원본 버퍼를 스레드로 넘겨 분리하지 않습니다. 고화질 정적 모델의 결합이 끝날 때까지 기존 기본 배치를 유지해 큰 네이티브 임시 복제의 생성을 줄입니다. 이는 작업을 분산하는 수정이며 전체 CPU 작업이 사라졌거나 실제 FPS가 측정되었다는 의미는 아닙니다.

## 좁은 항로와 탐사

- 조종 중심의 좌우 범위: ±42m → **±28m**. 일반 고도 상한: 62m → **52m**. 부드러운 가장자리, 필수 경로, 보상 위치, E의 좌우·복귀 고도도 함께 조정했습니다.
- 새 테마 모델을 한 구간에 최대 10종에서 **16종**으로 늘렸습니다. 해당 구간 코스에 이미 등장한 모델의 수집용 중복 배치를 줄이고, 좌우 가까운 구획에서 아직 사용하지 않은 모델을 우선 배치합니다.
- 새로 접근한 테마 풍경 8종마다 **탐사 보너스 600점**을 지급합니다. 동일 모델의 반복 관찰은 중복 지급하지 않습니다. 점수는 결과 보상 계산에도 반영됩니다.
- 한국 전통마을·산촌에는 강을 추가했습니다. 물이 없어 생성에서 제외되던 나룻배와 거북선이 이제 물 위에 등장합니다. 배의 움직임 경계 전체가 강·바다 위에 놓이는지 검사합니다.
- 슬라럼 장식 기둥이 필수 통과점 뒤의 방향 전환 공간을 막는 경우를 제거했습니다. 고속 항로 보정으로 통과 고도가 낮아질 때 지붕 모델도 균일하게 축소해 안전 여유를 유지합니다.

## 모델 수량의 구분

원본 ZIP은 403종입니다. 기체 22종과 환경 381종이며, 원본 시각 LOD 1,209개와 교통 보조 8개를 합쳐 1,217 GLB를 유지합니다. 원본 메시·텍스처·애니메이션을 이번 수정에서 삭제하거나 새로 생성하지 않았습니다. 모든 테마가 정확히 39종인 팩은 아닙니다.

## ZIP과 배포 용량

- 제공된 Edition9 ZIP: **532,821,338 bytes** (532.8 MB / 508.1 MiB).
- 서비스 API가 반환한 직전 배포 버전 8의 저장 아카이브: **227,584,000 bytes** (227.6 MB / 217.0 MiB), 일반 파일 2,175개.
- 원본 ZIP 전체를 그대로 웹에 올린 방식이 아닙니다. 기존 파이프라인이 무손실 Meshopt·gzip과 동일 이미지의 해시 공유를 적용합니다. 원본의 반복 이미지 11,655개는 공유 이미지 59개를 참조합니다. 상세 출처는 `ASSET-EDITION9.md`에 있습니다.
- 전체 배포 저장 크기, 전송용 압축 파일 크기, 브라우저가 한 테마에서 내려받는 파일 크기, 디코딩 후 메모리는 서로 다른 값입니다. 기본 테마 모델의 시각 파일은 테마당 약 1.6~2.6 MiB이며, 프록시·공유 이미지·기체·고화질 LOD는 추가됩니다.
- **214 MB라는 업로드 상한은 이번에 확인한 서비스 응답이나 공식 워크플로에 명시되지 않았습니다.** 이 숫자를 확인된 제한으로 안내해서는 안 됩니다.

전체 파일 및 테마별 전달 용량은 `validation/streaming-v4.2.json`에 기록합니다. 위 저장 아카이브 크기는 버전 8의 실제 서비스 응답이며, 4.2의 최종 아카이브 크기를 의미하지 않습니다.

## 검증 범위

- `continuous-flight`: 실제 `AirrunRenderer.frame()`과 물리 진행을 사용합니다. 최고 해상도 모델이 없는 상태로 192초·약 15.2km를 진행했고 출발 로딩 재진입은 0회입니다. 실제 GLB의 기본 모델이 고화질 요청 대기 중에도 CPU 장면에 남는지, 보이지 않는 충돌과 갑작스러운 근접 충돌 활성화를 막는지 검사합니다. 캐시 보존·해제와 요청 우선순위도 검사합니다.
- `theme-coverage`: 8개 테마와 한국의 4가지 변형, 2개 시드, 2종 기체의 **44개 사례**를 느린 28m/s로 180초 추적합니다. 원본 경계가 추적 카메라의 전방 프러스텀에 들어오는지를 검사합니다. 전체 덱이 42~112초 안에 한 번씩 등장했습니다. 배의 전체 이동 경계가 물 위에 있는지도 검사합니다.
- `audit-autopilot`: 22종 기체 × 레벨 1·10·20의 **66개 사례**에서 실제 조종·감속 코드를 사용해 모두 240초까지 첫 테마 전환 후 비행을 지속합니다.
- 기존 자산, 연속 충돌, 지형, 데이터 스트리밍, E 경로, 작업 스레드, 저장·진행·UI 계약 검사도 유지합니다. 실행 기록은 `validation/game-tests-v4.2.log`에 있습니다.

브라우저 제어 도구를 사용할 수 없어 이번 작업에서 실제 WebGL 화면, 휴대폰 조작, GPU 프레임 시간이나 사람이 느끼는 재미를 검증하지 못했습니다. 프러스텀 검사는 가려짐·안개·화면 가독성을 증명하지 않으며 CPU 통과 결과를 실제 기기 FPS로 표현하지 않습니다.
